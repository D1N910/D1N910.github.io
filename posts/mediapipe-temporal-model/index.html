MediaPipe + 轻量时序模型：动作识别流水线笔记

October 29, 2026

这是一篇额外笔记，记录 TFLite、MediaPipe 和轻量时序模型的概念，以及一种可落地的动作识别流水线。与 YOLO26 论文笔记分开，方便以后做健身动作识别项目时直接查。

1. TFLite 推理图、CNN、MediaPipe 图的关系

三者不是同一层概念，不能直接二选一。

概念 是什么 关注点
CNN 模型架构：卷积层、池化、激活、残差怎么连 表达能力、精度
TFLite 推理图 部署产物：转成 .tflite 后的可执行计算图 延迟、内存、算子兼容、量化、GPU/NPU 委托
MediaPipe 图 流水线编排：预处理 → TFLite 推理 → 后处理 整条链路的连接、同步、输入输出

层次关系：

CNN（模型架构）
  → TFLite 图（单个模型的可执行图）
  → MediaPipe 图（整条推理流水线，可能包含多个 TFLite 模型）
  • CNN 是菜谱：描述用什么层、怎么算。
  • TFLite 图是打包好的料理包 + 厨房适配说明：描述在手机上按什么顺序执行哪些算子、张量多大、权重在哪、是否量化。
  • MediaPipe 图是整条厨房流水线：备菜、加热、装盘怎么衔接。

TFLite 图可以装 CNN，也可以装 LSTM、Transformer；CNN 也可以导出成 TFLite 图。所以“TFLite 推理图 vs CNN”不是对立关系，而是部署形态与模型架构的关系。

2. 两段式动作识别流水线

视频帧
→ MediaPipe Pose（每帧检测 33 个关键点）
→ 关键点序列（T×33×4：x, y, z, visibility）
→ 下游时序模型（LSTM / GRU / 1D-CNN / TCN / Transformer）
→ 动作、相位、错误标签
→ 规则映射成指导文案
  • 保留 MediaPipe 做推理：不自己训练姿态模型，继续用 MediaPipe 的预训练姿态模型提取每帧关键点。它内部也是 CNN + TFLite，可以当黑盒用。
  • 下游时序模型：在关键点序列上单独训练一个模型，学习动作随时间的变化。MediaPipe 负责“关节在哪”，时序模型负责“你在做什么动作”。
  • “下游”：MediaPipe 是上游特征提取器，时序模型是下游任务模型。

为什么这么设计

  • 复用成熟的姿态模型，省数据、省训练成本；
  • 关键点维度低，时序模型可以很小，端侧跑得动；
  • 模块化：姿态模型和动作模型可以分别替换、分别调试；
  • 隐私友好：关键点可以在本地处理，不必上传视频。

代价

  • 误差传播：MediaPipe 关键点错了，下游模型跟着错；
  • 丢失外观信息：只看骨架，器械、物体交互看不到；
  • 两段式延迟和集成复杂度；
  • 需要标注动作片段，窗口大小、步长、平滑策略都要调；
  • 遮挡、健身房器械、特殊机位可能让 MediaPipe 失效。

3. 轻量时序模型是什么

它不是只看单帧，而是输入一段时间的特征序列，基于整段序列做判断。

类型 特点 适合场景
1D-CNN / TCN 在时间维做卷积，快、易并行 固定窗口的动作分类
GRU / LSTM 循环网络，能处理变长序列 动作相位、连续判断
小 Transformer 注意力建模长依赖 数据多、序列长
窗口统计 + MLP 均值、方差、最大值等统计特征 最便宜的 baseline

“轻量”指参数量小、端侧能跑，目标通常是 <1M 参数，TFLite INT8 后几毫秒级。真正占延迟的是 MediaPipe 姿态模型，不是这个时序模型。

4. 输入与输出设计

输入窗口

输入 10 帧 MediaPipe 特征方向是对的，但 10 帧太短：30 FPS 下只有 0.33 秒，而深蹲一次通常 2–3 秒。10 帧只能判断“当前相位”，判断不了完整动作。

建议：

  • 动作分类：30–60 帧窗口，stride 5–10；
  • 或者用“相位模型 + 状态机”做计数：下蹲 → 底部 → 起身 → 计数 +1。

特征

  • 33 个关键点 × 4（x, y, z, visibility）；
  • 关节角：膝、髋、踝、肘等；
  • 角速度/位移速度；
  • 按髋中心和躯干长度归一化；
  • 用 visibility 做缺失掩码。

输出：多任务结构化标签

不建议一个 softmax 直接吐“动作 + 是否标准 + 指导文案”，而是拆成结构化多任务：

输入：T×F 特征（关键点 + 关节角 + 速度 + visibility）
  ├─ 动作头：深蹲 / 卧推 / 硬拉 ...        （softmax）
  ├─ 相位头：下蹲 / 底部 / 起身 / 站立      （softmax）
  ├─ 错误头：膝盖内扣 / 深度不足 / 背部前倾 / 脚跟离地 ...（多标签 sigmoid）
  └─ 质量分：由错误标签和阈值算出来，不一定单独训练

输出示例：

{
  "action": "squat",
  "action_confidence": 0.93,
  "phase": "bottom",
  "errors": [
    {"type": "knee_valgus", "severity": 0.8},
    {"type": "insufficient_depth", "severity": 0.4}
  ],
  "is_standard": false,
  "guidance": "膝盖与脚尖方向保持一致，下蹲再深一点"
}

5. 指导文案：规则映射，不让模型直接生成

时序模型只输出结构化错误标签，指导文案用规则/模板映射：

if knee_valgus > 0.6: "膝盖与脚尖方向保持一致"
if depth < 0.5:       "下蹲再深一点，髋部低于膝盖"
if back_angle > 30:   "保持背部中立，避免弯腰"

这样可测试、可解释、不会幻觉。需要更自然的措辞时，再把结构化错误交给 LLM 润色，但检测结果仍由模型和规则决定。

6. 最小可行方案

  1. 特征：33 个关键点 × 4 + 关节角 + 角速度；按髋中心和躯干长度归一化，用 visibility 做缺失掩码。
  2. 窗口：30 帧 @30FPS，stride 5–10；不足补零或截断。
  3. 模型：1D-CNN 或 GRU，hidden 64–128，先别上 Transformer。
  4. 标签：动作类别 + 错误类型多标签；不要只标“标准/不标准”，否则没法生成具体指导。
  5. 后处理：滑动窗口投票/平滑；深蹲计数用膝角峰值或相位状态机，不要靠单帧分类。
  6. 兜底：关键点置信度低时输出“请调整机位”，而不是硬判。

7. 两个容易踩的坑

  • “是否标准”必须先有 rubric：深蹲的标准是什么？膝盖内扣、深度、背部角度、脚跟离地，各自阈值多少？没有定义就没法标注，也没法评估。
  • 单目 2D 关键点有遮挡和视角问题：健身房器械遮挡很常见；先做关键点质量监控，再谈动作准确率。

8. 和 YOLO26-pose 的关系

如果 MediaPipe 在深蹲、卧推等场景关键点不稳，可以把上游换成 YOLO26-pose；下游时序模型的接口不变，只换关键点来源和格式映射。这是后续的可选升级路径，不是第一版必须做的事。

9. 下一步

  • 定义动作 rubric 和错误类型（深蹲、卧推、硬拉各一套）
  • 采集并标注 30–60 帧的动作片段
  • 统计 MediaPipe 关键点质量（遮挡、视角、置信度分布）
  • 训练 1D-CNN / GRU baseline
  • 加规则映射和状态机计数
  • 评估 per-class accuracy/F1、端侧延迟和失败案例

一句话总结：MediaPipe 负责看关节，时序模型负责看变化，规则负责说人话。
