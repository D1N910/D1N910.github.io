第 03 记｜2026-11-16 · 1.1 RAG 简介：开卷考试、演进三阶段与「RAG 已死？」

依据：本人录制的口述 vlog（录屏 2026-11-16 22.50.40.mov，27 分 40 秒，转录全文带时间戳），对应教程 docs/chapter1/01_RAG_intro.md。以下是口述整理稿，保留当时的理解和疑问；转录误识别的术语（IG→RAG、HYYDE→HyDE、longchain→LangChain 等）已还原。

这节学了什么

  • RAG 是什么：Retrieval-Augmented Generation，检索增强生成。解锁大语言模型「知其然不知其所以然」的技术范式 —— 把模型的参数化知识（训练时固化的记忆）和非参数化知识（可随时更新的外部数据）结合起来。
  • 两阶段架构：检索阶段用嵌入模型把知识库编码成向量索引，查询时也向量化，靠相似度检索召回相关内容；生成阶段把检索到的文档和用户的原始问题一起送进 prompt，引导 LLM（比如 DeepSeek）有理有据地生成。
  • 技术演进三阶段：Naive RAG（索引 → 检索 → 生成）→ Advanced RAG（检索前查询重写、检索后重排过滤）→ Modular RAG（动态路由、查询转换、多路融合、编排与循环）。
  • 为什么用 RAG：提示词工程 → RAG → 微调的取舍路径；本质是「更依赖外部上下文」还是「更依赖模型本身」。
  • 配套组件：LangChain / LlamaIndex 框架、向量数据库、最小可行系统四步、评估方式（检索相关性 + 生成质量）。

关键笔记 / 代码片段

① 开卷考试与两阶段

  • 我自己用的比喻：LLM 训练完就学了东西，但考的内容不一定都学过；它旁边有一本书（外部资料），可以翻书答。开卷考试，既能用学到的，也能查资料。
  • 嵌入模型把知识库编码成向量索引，「就相当于是 ID」。我拿图书馆打比方：书先按类别编码放好，科学类放一块、有编号，按号查。
  • 相似度检索：「一个 A 向量一个 B 向量，看方向是不是保持一致，这叫同向而行」，同向就认为相关。
  • 生成阶段：「把用户这个问题，还有根据这个问题从知识库里搜的东西一起拉过来」，按预设 prompt 引导模型输出。
  • 我自己的延伸：搜到的东西不一定真相关，这取决于检索阶段的能力。prompt 指令就像同一个问题抛给农业学家、生物学家、数学家，思考方式不一样 ——「我做我这个模块的，可能就得有专门的一个 prompt」。

② 三阶段演进（口述原话整理）

  • Naive RAG：傻瓜式，索引 → 检索 → 生成。
  • Advanced RAG：索引后加「预检索」——查询重写，问的是 A，先拓展再检索；检索后加「后检索」——重排序过滤，「检索出 100 个知识点，我只要前 10 个，排个序看重要性」。
  • Modular RAG：索引阶段做 chunk 优化——小块 / 单句检索，再带上父级更大的块和上下文，也就是 small to big；组织方式上有结构化分层（PDF → 章节 → 块）和知识图谱（师兄师姐做过，我自己没做）。
  • 我给模块化 RAG 的一句话：「把『我爱你，你爱不爱我』这种很普通的话，通过检索变得语义丰富 —— 变成地球上的我，不是火星上的我。」
  • 离线 vs 在线：索引建立是离线提前准备的；用户一问才检索、生成是在线。
  • 模块化关键组件：动态路由、查询转换、多路融合。

③ HyDE、查询改写与编排（当时不懂，边查边记）

  • 图里出现 HyDE 我不知道是什么，问了语音助手才查到：「假设性文档嵌入」。把一句简单问题（「深圳电动车上牌」）扩写成「今天早上我要去深圳，我要给深圳电动车上牌」这种假设性文档，再拿它去检索相似文档，「可能会找到更多的东西」。
  • 查询变形 / 扩张：一个问题拆成子问题（什么是电动车、什么是上牌……）；查询结构化则是 Text2SQL / Text2Cypher 那类（当时不懂）。
  • 检索环节：混合检索（嵌入 + 关键词）、检索来源（句子块 / 文章）、检索器选择；检索后重排、压缩、再让大模型挑哪些可用。
  • 验证环节：拿外部知识核对是不是幻觉、问题到底能不能回答、有没有隐私内容；答不上就再走一轮 RAG。
  • Orchestration（编排）：我翻译成了「管弦乐队」。路由判断——难问题必须从知识库找，简单问题如 1+1=2 直接让 LLM 自己答；调度——判断要不要检索、生成后要不要再检索，循环应该有次数限制。编排产生的推理和检索结果还能回流到知识图谱，反过来增强检索。

④ 提示词 → RAG → 微调：我的取舍

  • 教程路径：提示词能搞定就先用提示词；不行上 RAG；还不行才微调（把知识强制学进模型，「不需要旁边挂一个字典」）。
  • 图上两条轴：越依赖上下文越要 RAG，越依赖模型本身越要微调。我当时就觉得两者结合才是好方向。
  • 我的理由：微调要从头微调一遍，增量微调可能会遗忘，「就像人一样」；RAG 接上知识后原有能力不丢失，新知识只要更新 RAG，不用重训模型 ——「所以我觉得这个当然是好的方向」。
  • 反例也记：像飞 5.2 / ChatGPT 这类模型，提示词一搞答案就出来，那种场景确实不用 RAG 也不用微调；公司自己的知识、豆包嵌进飞书做的企业内 RAG，才是 RAG 的主场。

⑤ RAG 解决什么、怎么评估

  • 静态知识局限（训练完就固定，最新知识靠外部动态更新）、幻觉（先保证 RAG 里的知识是新的、别有错、别像 NPD 一样撒谎）、法律医疗这类严肃场景的可信度、隐私与本地知识。
  • 多元集成：换更好的检索组件就行，「我已经有一个大模型部署好了，只需要时不时给他换一个脑子」。
  • 最小可行系统（顺着教程捋的四步）：① 数据准备与清洗——PDF / Word 标准化，按语义切块而不是随便截字符，避免信息支离破碎；② 索引构建——块转向量存库，关联原数据来源、页码、章节；③ 检索优化——混合检索 + 重排；④ 生成——prompt = 问题 + 上下文 + 规则。
  • 快速验证：Dify、FastGPT 这类可视化平台把复杂 RAG 封装好了，上传就能用；自己开发就用 LangChain / LlamaIndex。
  • 评估两块：检索相关性（找到的东西是否包含答案）、生成质量（语义准确性 + 词汇匹配度 / 专业用词是否得当）。
  • 优化方向：性能上索引分层找得更快、多模态扩展找得更全；架构上用分支 / 循环替代纯线性——「第一次找不对，第二次再找」，鲁棒性更强。关于「线性做准了是不是也一样好」，我自己是犹豫的：先说「一样可以搞得很好嘛」，又说「还是复杂的设计更稳一点吧」——留着这个犹豫，后面用实践验证。

第 07 记｜2026-11-20 · 2.2 文本分块：上下文限制与池化的信息损失

依据：本人的学习笔记，对应教程 docs/chapter2/05_text_chunking.md。Task 2 继续，从「为什么要分块」切入。

这节学了什么

  • 文本块大小是有上限的，不是想切多大就切多大：它同时受限于两个模型 —— 嵌入模型的上下文窗口（比如 bge-base-zh-v1.5 是 512 token，超了会被截断、向量无法完整代表原文）和 LLM 的上下文窗口（检索到的块 + 问题 + prompt 都得塞进去，块太大就只能放少数几个块，参考广度下降）。
  • 不是越大越好。嵌入模型最后要把整个文本块压成一个向量，这个压缩过程必然丢信息；块越长，语义点越多，单一向量承载的信息越稀释。
  • 看了其他框架的分块策略：Unstructured（基于文档元素）、LlamaIndex（结构感知的 Node Parser）、ChunkViz（分块可视化）。

关键笔记 / 代码片段

① 池化（Pooling）：为什么长块会糊

  • 做法：通过某种方法（取 [CLS] 位的向量、对所有 token 向量求平均 mean pooling 等），把所有 token 的向量压缩成一个单一向量，用它代表整个文本块的语义。
  • [CLS] 是 BERT 等 Transformer 在输入文本开头加的特殊标记，通过自注意力机制动态聚合整个序列的上下文，最终向量被训练用来代表全局语义。
  • 关键推论：一个 768 维的向量要概括整个文本块的所有信息。文本块越长，语义点越多，这个向量承载的信息就越稀释 —— 表示变得笼统、关键细节被模糊化，检索精度下降。
  • 另一头也有问题：即使把多个大块塞进 LLM 的长上下文，关键信息也会被「淹没」在大量无关内容里；长上下文里模型更容易记住开头和结尾、忽略中间（lost in the middle）。

② 其他开源框架的分块策略

框架 做法 适用
4.1 Unstructured 基于文档元素的智能分块：先分区出 Title / NarrativeText / Table 等元素，再组合成块；by_title 会把 Title 当新章节起点 版式复杂的文档，「先理解、后分割」
4.2 LlamaIndex 节点（Node）解析与转换：结构感知型解析器如 MarkdownNodeParser、JSONNodeParser、CodeSplitter，还有 SentenceWindowNodeParser 文档里涉及很多 markdown、JSON 或代码时用（我看到的点）
4.3 ChunkViz 把文档和分块配置作为输入，用不同颜色块展示每个 chunk 的边界和重叠 分块后可视化看效果，调参时很直观

  • 暂无实操踩坑（这节偏概念）。
  • 一个容易混的点记一下：chunk_size 只是「目标大小」，实际切块还要看分隔符、段落完整性和重叠（chunk_overlap）；教程示例里出现过注释写 100 但实际参数 200 的笔误，读代码时以参数为准。

这节学了什么

关键笔记 / 代码片段

① 权限问题的两个坑

  • wget ... -O docker-compose.yml 报 Permission denied：是写权限被拒（不是网络问题），当前用户 ubuntu 不能往 /workspace 写文件。解决：

    sudo chown -R ubuntu:ubuntu /workspace

    chown = change owner，-R = 递归（目录 + 里面所有文件子目录全部生效），ubuntu:ubuntu = 所有者改 ubuntu、所属组改 ubuntu。

  • sudo docker compose up -d 报 dial unix /var/run/docker.sock: connect: permission denied：ubuntu 不在 docker 组，连不上 Docker 守护进程。两条路：

    sudo docker compose up -d                    # 临时：每次加 sudo（我选这个）
sudo usermod -aG docker $USER; newgrp docker # 一劳永逸：加组并立即生效

    那条 version is obsolete 只是警告，compose 里的 version: 字段过时会被忽略，不影响运行，删掉更清爽。

② 召回率怎么算

召回率 = TP / (TP + FN)
记号 全称 含义
TP True Positive 相关，也召回了
FN False Negative 相关，但漏掉了
FP False Positive 不相关，却召回了
TN True Negative 不相关，也没召回（不算进召回率）
  • 分母 TP + FN = 所有真正相关的文档，分子 = 找回来的相关文档。例：10 个相关、找回 4 个 → 40%。
  • 分母需要「标准答案」：要先人工标注每个问题相关的块（ground truth），才能算。
  • 常见写法 Recall@k（k = 返回的 top-k 数量）：k 越大召回越高，但会带回更多无关内容。
  • 与精确率（Precision = TP / (TP + FP)）取舍：调大 k → 召回升、精确降；加 rerank → 精确升。RAG 里一般先追高召回（相关内容没进上下文，LLM 再强也答不出），再靠重排提精确 —— 接上第 03 记里 Advanced RAG 的「检索后重排」。

② 工作原理（照图的流程）

关键笔记 / 代码片段

① 倒排文件索引（IVF, Inverted File Index）

借的是搜索引擎「倒排索引」的思路：正排是「文档 → 词」，倒排是「词 → 哪些文档」。放到向量上：

步骤 做什么 类比
1. 聚类分桶 用 k-means 把向量分成 nlist 个桶，每桶一个中心点 把书按主题分到书架
2. 建倒排表 记录「桶 → 里面有哪些向量」 每个书架的藏书清单
3. 查询 算查询向量跟各桶中心的距离，挑最近的 nprobe 个桶 先定位到相关书架
4. 精搜 只在这几个桶里做精确相似度计算 只在这几个书架找书
  • 参数：nlist = 桶数；nprobe = 查询搜几个桶。nprobe 越大召回越高但越慢（接第 12 记召回率）——相关向量落在没搜的桶里就漏了，所以 IVF 召回不是 100%。

② HNSW（Hierarchical Navigable Small World，分层可导航小世界图）

词 含义
Hierarchical 分层 图分多层，像跳表：上层稀疏、下层密集，从顶层定位、逐层精细
Navigable 可导航 每个节点知道自己的邻居，搜索像顺着路网跳
Small World 小世界 任意两点几步可达（六度分隔那个「小世界」）
  • 快的原因：从顶层入口出发，每次跳到「离目标更近」的邻居，像贪心爬山；上层跨大步、下层精定位。
  • 参数：M = 每节点最大连接数（越准但越吃内存）；efConstruction = 建索引时搜索范围（质量高但慢）；ef = 查询时遍历深度（越大召回越高但越慢） —— 跟 IVF 的 nprobe 是同类角色。
  • 记法：HNSW = 分层小世界图，靠跳邻居快速逼近；ef 调召回，M 调内存。

③ 图像拼图：panoramic 不是 360° 全景

在这段代码里 panoramic 是「把多张小图拼成一张大图」：

panoramic_width  = img_width  * row_count
panoramic_height = img_height * row_count

宽高都乘 row_count → 拼成 row_count × row_count 的网格（如 3×3）。

④ np.full 造白画布

panoramic_image = np.full((panoramic_height, panoramic_width, 3), 255, dtype=np.uint8)

创建一个所有像素填 255（白） 的 RGB 图像数组：(高, 宽, 3) = 图像形状，3 通道；dtype=np.uint8 = 像素 0–255 的标准类型。后面把检索到的图贴上去，没贴到的地方留白。

query_display_area = np.full((panoramic_height, img_width, 3), 255, dtype=np.uint8)

另一块白布：高度同大图、宽度只有一张图宽 → 像是旁边留一条竖栏放查询文字/说明。

⑤ [:, :, ::-1] 通道倒序（RGB → BGR）

query_pil = Image.open(query_image_path).convert("RGB")   # PIL：RGB
query_cv  = np.array(query_pil)[:, :, ::-1]              # 转成 BGR 给 OpenCV
切片 含义
[行, 列, 通道] 三维数组三个轴
: / : 行、列全取
::-1 通道轴从后往前取，倒序 → [R,G,B] 变 [B,G,R]

原因：PIL 用 RGB，OpenCV 用 BGR（历史遗留），不转的话 cv2.imshow / imwrite / putText 显示会偏色（红蓝互换）。反过来转 PIL 再倒一次：Image.fromarray(cv_img[:, :, ::-1])。小坑：[:, :, ::-1] 是视图不是拷贝，要修改就加 .copy()。

⑥ .eval() 是 PyTorch 的评估模式

model.eval()              # 切到评估/推理模式
with torch.no_grad():     # 不计算梯度，省显存加速
    output = model(input)
  • eval() 关掉训练时的两个行为：Dropout（不再随机丢神经元）、BatchNorm（用全局统计而非当前 batch）。
  • 目的：推理结果稳定可复现；不调也能跑，但同输入每次结果可能不同。
  • 别和 Python 内置函数 eval("1+2") 搞混——那个是把字符串当代码执行，带风险，跟模型无关。

⑦ 检索结果可视化：把查询图贴进竖栏并打标签

接着④⑤，这段把「查询图」处理完贴进 query_display_area：

resized_query = cv2.resize(query_cv, (img_width, img_height))                    # 统一尺寸
bordered_query = cv2.copyMakeBorder(resized_query, 10, 10, 10, 10,
                                    cv2.BORDER_CONSTANT, value=(255, 0, 0))     # 加边框
query_display_area[img_height * (row_count - 1):, :] = \
    cv2.resize(bordered_query, (img_width, img_height))                          # 贴到底部那块
cv2.putText(query_display_area, "Query", (10, panoramic_height - 20),
            cv2.FONT_HERSHEY_SIMPLEX, 1, (255, 0, 0), 2)                         # 写标签

逐个说：

  • cv2.resize：统一成 img_width × img_height，才能贴进固定大小的格子。第二个参数是 (宽, 高)，跟 numpy 的 (高, 宽, 通道) 顺序相反，别写反。缩小时可指定 interpolation=cv2.INTER_AREA 更清晰。
  • cv2.copyMakeBorder(..., 10,10,10,10, cv2.BORDER_CONSTANT, value=(255,0,0))：上下左右各加 10px 边框，纯色填充（BORDER_CONSTANT）；其他模式还有 BORDER_REPLICATE（复制边缘）、BORDER_REFLECT（镜像）。给查询图加框是为了在结果里一眼认出来。
  • query_display_area[img_height*(row_count-1):, :]：竖栏的最后一块（高度正好 img_height，宽度全取）；把带框的查询图 resize 回格子大小贴进去。resize 回去时边框也一起被压缩，会变细但还在。
  • cv2.putText：在图上写字。参数依次是：图、"Query"、(x,y) 坐标（文字左下角，原点在左上角）、字体 FONT_HERSHEY_SIMPLEX、缩放倍数 1、颜色 (255,0,0)、线宽 2。
    • putText 没有「默认字号」，那个 1 就是必须传的 fontScale；SIMPLEX 在 scale=1 时字高约 20px，2 就是两倍，可传小数。
    • 精确控制像素高度：先 cv2.getTextSize("Query", font, 1, 2) 量出 (text_w, text_h)，再 scale = 目标高度 / text_h 反推。加 cv2.LINE_AA 抗锯齿更平滑。
    • 字放大后注意别超出图边界被裁掉，用 text_w 检查右侧空间。

踩坑与解决

  • 概念坑：panoramic 在这段代码里不是「360° 全景图」，是「拼图」——看词之前先看上下文。
  • 参数对照记牢：IVF 的 nprobe 和 HNSW 的 ef 都是「查询时多搜一点 → 召回高但慢」，本质是同一个权衡。
  • 颜色坑又出现一次：value=(255,0,0) 和 putText 的 (255,0,0) 在 BGR 下都是蓝色，不是红色；红色要写 (0,0,255)。写颜色前先想「这是给 cv2 的」。
  • resize 的参数顺序 (宽, 高) 跟数组 (高, 宽) 相反，拼图代码里容易写反。

依据：本人的学习笔记，对应教程 docs/chapter3/10_index_optimization.md（第 3 章第五节「索引优化」）。这一记只做了了解，代码没去实现 —— 如实标注，不冒充跑过。

这节学了什么

  • 索引优化解决的核心矛盾：小块检索精确但缺上下文（LLM 答不好），大块上下文丰富但引入噪音（检索相关性低）。
  • 两条思路，都只做了了解：
    1. 上下文扩展（句子窗口检索）—— LlamaIndex 提出的策略
    2. 结构化索引 —— 给文本块附加结构化元数据，检索时先过滤再搜

关键笔记 / 代码片段

① 上下文扩展：句子窗口检索

一句话思想：为检索精确性而索引小块，为上下文丰富性而检索大块。

三阶段流程：

阶段 做什么
索引阶段 文档切成单个句子，每句作为一个 Node 存入向量库；该句的前 N 句 + 后 N 句（默认各 3 句）作为上下文窗口存进该 Node 的元数据 —— 窗口文本不被索引，只做元数据
检索阶段 用单句做精确匹配（小块 = 高精度）
后处理阶段 MetadataReplacementPostProcessor 读取命中节点的元数据，用完整窗口替换原来的单句内容，再送给 LLM
  • 关键细节：SentenceWindowNodeParser 会把 window、original_text 加进 excluded_embed_metadata_keys / excluded_llm_metadata_keys —— 告诉嵌入模型和 LLM 忽略这两个字段，保证只用干净的单句做检索。
  • 效果（教程对比）：句子窗口检索的答案更详尽连贯，会补充「定量预测置信度低」「观测记录过短」等多个维度，信息量更大。

② 结构化索引：元数据过滤 + 递归检索

  • 原理：索引文本块时附加结构化元数据（文档类型、年份、季度、标题等），检索时把元数据过滤和向量搜索结合。
  • 接第 07 记：第 2 章的 MarkdownHeaderTextSplitter 把标题提取进元数据，就是结构化索引的前置步骤。
  • Example：查「2023 年 Q2 财报里关于 AI 的论述」→ 先按 document_type='财报'、year=2023、quarter='Q2' 预过滤，再在子集里做向量搜索。
  • 递归检索（多表格场景，如 Excel 多个 Sheet）：
    • 建两个索引：摘要索引（每个 Sheet 一句话摘要，充当路由器）+ 内容索引（实际数据，附 {"sheet_name": "年份_1994"} 元数据）
    • 查询两步：先路由（在摘要索引里匹配到目标 Sheet）→ 后检索（用 MetadataFilter 强制只在该 Sheet 里搜）
    • 核心组件 RecursiveRetriever，用 query_engine_dict 把节点 ID（工作表名）映射到对应的查询引擎
    • 教程还给了「不走代码执行」的另一种实现：摘要索引路由 + 内容索引元数据过滤，避免执行代码的安全隐患

踩坑与解决

  • 这节代码没实现，所以没有实操踩坑 —— 只有概念层面的理解，别当成「跑通了」。
